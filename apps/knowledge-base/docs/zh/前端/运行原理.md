
## JavaScript 运行时模型

JavaScript 代码的执行逻辑由ECMAScript规范、JS 引擎、宿主环境三者共同支撑：

- ECMAScript（简称 ES）是 JavaScript 的语言标准，它从规则层面定义了代码的语法和语义，如基础类型、语法规则、执行上下文、词法环境、作用域机制等；
- JavaScript 引擎：引擎是规范的具体实现，负责把 JS 代码解析、编译为机器码并执行，同时管理内存分配与垃圾回收；
- 宿主环境：宿主是 JS 引擎的运行载体，它向引擎注入语言之外的 API，并调度代码的执行时机，如浏览器、Node.js等；

### 执行上下文

执行上下文是 ECMAScript 规范中的抽象概念，是 JS 代码运行时的环境容器，代码每进入一段可执行代码（全局、函数、eval），就会创建一个执行上下文，存放这段代码执行需要的全部状态信息；

执行上下文栈：管理多个执行上下文，后进先出，栈顶是正在运行的上下文；

常见执行上下文：

- 全局执行上下文：执行经典脚本（`<script>`）的全局代码时创建，整个程序只有一个，位于调用栈最底部；
- 函数执行上下文：每次函数调用都会创建，调用即创建，返回即销毁，可重复创建；
- 模块执行上下文：执行 ES Module 代码时创建，拥有独立的顶层作用域；
- eval 执行上下文：执行 `eval()` 代码时创建，继承调用位置的词法环境；

执行上下文是 ECMAScript 标准定义的语义模型，作用是统一约定代码执行的行为规则，它并不直接等同于某块具体的物理内存。 不同的 JavaScript 引擎（V8、JavaScriptCore 等）可以基于自身架构，采用栈帧、寄存器分配、即时编译优化等不同的底层技术实现，只要最终表现出的语言语义和规范一致即可；

执行上下文包含关联的 Realm 运行域、Script/Module 代码载体、词法环境、变量环境、类私有环境，以及 this 绑定、new.target 等运行时状态，承载着标识符解析与代码执行所需的全部信息

#### 词法环境

词法环境（LexicalEnvironment）：用于保存函数/const/let的变量绑定，控制作用域查找规则；包括环境记录 + 外部词法环境引用：

- 环境记录：存储当前作用域`let` / `const` / `function` / class声明的标识符（变量名 / 函数名），环境记录种类包括：

	- 声明式环境记录：函数作用域、普通块级作用域 `{}`、`catch` 子句等绝大多数常规作用域的记录；
	- 对象环境记录：`with` 语句作用域的记录；

- outer 外部引用：指向外层词法环境，形成作用域链。当当前环境找不到变量，沿着 outer 向上查找，直到全局；

`LexicalEnvironment` 在代码执行阶段会动态变化，例如块作用域（if/for/{}）会在进入块时新建一个词法环境；

```
function foo() {
  let a = 10; // 存放在 LexicalEnvironment
  {
    let b = 20; // 新建子 LexicalEnvironment，outer 指向 foo 的词法环境
    console.log(a); // 顺着 outer 找到 a
  }
}
```

#### 变量环境

变量环境（VariableEnvironment）：早期 ES3 词法环境和变量环境是同一个，在ES5 拆分出来了，用于存放专门存放 var 声明的变量绑定（把一个标识符和一个值建立关联，并把这个关联关系注册在环境记录里的操作）；核心特性：

- VariableEnvironment 也是一个词法环境对象，结构和 LexicalEnvironment 一样。
- 函数执行时：VariableEnvironment 在函数创建时就确定，整个函数执行期间不会改变；而 LexicalEnvironment 在遇到块作用域时会替换。
- `var` 变量提升，绑定注册在 VariableEnvironment；`let/const` 注册在 LexicalEnvironment。

```
function test() {
  var v = 1; // 绑定在 VariableEnvironment
  let l = 2; // 绑定在 LexicalEnvironment
}
```
#### 私有环境

私有环境（ PrivateEnvironment）：专门用于class 私有成员 `#xxx`；

- 保存当前类作用域下私有名称的绑定；
- 私有名称不是普通字符串，是 JS 内部唯一的私有符号，不能直接外部访问；
- PrivateEnvironment 通过 outer 连接词法上嵌套的类，用于解析嵌套类中可见的私有名称；它不表示类继承关系，子类也不能直接访问父类声明的私有字段；

```
class Demo {
  #secret = 123; // #secret 这个私有名称，记录在 PrivateEnvironment
}
```

#### Realm（域）

当前 Realm（域）：所有执行上下文都关联一个 Realm，Realm 是一套完整、自给自足且相互隔离的 JavaScript 运行沙箱环境：同一个 Realm 内的所有执行上下文共享同一套基础运行设施；不同 Realm 之间的环境完全独立，互不污染；包含：

- 全局对象和globalThis：浏览器环境中全局对象是 `window`，Node.js 环境中是 `global`，在ES2020 引入 `globalThis`，统一指代当前 Realm 的全局对象，用于跨宿主环境兼容；
- 内置对象：JS 语言原生提供的构造函数和工具对象，如`Array`、`Date`、`Promise` 等；
- 全局变量环境（全局作用域）：是整个 Realm 唯一的最外层作用域，是所有作用域链的终点，所有局部作用域的词法环境最终都会通过 `outer` 指向它；

常见的独立 Realm 场景：浏览器的每个标签页、每个 `<iframe>`，浏览器的 Web Worker，Node.js 的每个 worker 线程， 同页面内所有 `<script>` 标签，共享同一个 Realm；

#### Script/Module 代码载体

当前关联的 Script 或 Module 对象：每个执行上下文内部都有一个 `ScriptOrModule` 属性，指向创建该上下文的原始代码载体，用来区分当前代码是普通脚本（Script）还是 ES 模块（Module）。二者在顶层作用域的运行规则存在本质差异：

- Script：顶层代码的 `this` 指向当前 Realm 的全局对象 `globalThis`，顶层通过 `var` 声明的变量、`function` 声明的函数，会自动挂载为全局对象的属性；
- Module：顶层代码的 `this` 值为 `undefined`，顶层无论用 `var`、`let` 还是 `const` 声明的变量，都不会挂载到全局对象上；

#### this 绑定

`this` 不是普通变量，不能像普通标识符一样通过作用域链解析。普通函数调用通常会建立本次调用对应的 `this` 绑定，其取值主要由调用方式决定；箭头函数不创建本地 `this` 绑定，而是沿词法环境使用外层提供的 `this`；

#### new.target

`new.target` 是 ES6 新增的、专属于函数执行上下文的内部属性，用于检测函数的调用方式：

- 当函数通过 `new` 关键字调用（构造函数模式）时，`new.target` 的值就是被 `new` 的构造函数本身
- 当函数以普通方式调用时，`new.target` 的值为 `undefined`

它可以用于要求普通构造函数必须通过 `new` 调用，避免普通调用引发的 `this` 指向错误和全局污染。`class` 构造器本身就不能脱离 `new` 调用，因此这里使用普通函数演示：

```
function Person() {
  if (!new.target) {
    throw new Error('必须使用 new 关键字调用 Person 构造函数');
  }
}

new Person(); // 正常
// Person(); // 抛出错误
```

### 调用栈

调用栈是 JavaScript 引擎管理函数执行顺序的核心机制，本质是一个后进先出（LIFO）的栈结构，用于跟踪当前正在执行的函数调用链路，保证代码执行顺序与语义一致；

每调用一个函数，引擎就会创建一个对应的执行上下文（也叫栈帧），并将其压入调用栈顶端；函数执行完毕（正常返回或异常抛出），对应的执行上下文就会出栈，控制权交还给栈顶的下一个上下文；

栈帧本身只存执行状态和指针，变量本体不一定存在栈帧里：普通局部基本类型直接存在栈帧槽位中，被闭包捕获的变量、引用类型对象本体都存在堆内存中，栈帧只保存引用地址；

```
function first() {
  second();
}

function second() {
  third();
}

function third() {
  console.trace();
}

first();
```

**执行流程：**

1. 脚本加载：创建全局执行上下文（`global`），压入调用栈，开始执行全局同步代码
2. 调用 `first()`：`first` 函数执行上下文压入栈顶
3. `first` 内调用 `second()`：`second` 执行上下文压入栈顶
4. `second` 内调用 `third()`：`third` 执行上下文压入栈顶
5. 执行 `console.trace()`：此时栈顶到栈底依次为 `third → second → first → global`
6. `third` 执行完毕：出栈
7. `second` 执行完毕：出栈
8. `first` 执行完毕：出栈
9. 调用栈回到仅全局上下文的状态，等待后续任务触发；

全局执行上下文不是栈底永久元素：

- 它只在当前这段全局同步代码执行期间存在；
- 全局所有同步逻辑执行完毕后，全局执行上下文会弹出，调用栈变为空；
- 调用栈彻底为空，是事件循环取出下一个异步任务执行的硬性前提；

**栈溢出**：调用栈的容量是有限的（V8 引擎默认栈深度约 1 万～几万层，不同引擎有差异），当入栈的上下文数量超过上限时，就会抛出 `RangeError: Maximum call stack size exceeded`；

```
function recurse() {
  recurse(); // 没有终止条件，持续压栈
}
recurse(); // 栈溢出报错
```

**异步代码与调用栈的关系**：异步回调不会延续原调用栈。回调函数在后续任务中执行时，会建立一个全新的调用栈，和原调用栈没有物理关系

```
function foo() {
  setTimeout(() => {
    console.trace();
    // 真实运行栈只有：回调函数 → global，没有 foo
  }, 0);
}
foo();
```

- 执行 `setTimeout` 时，回调函数会被交给 Web API 管理，`foo` 执行完毕后直接出栈，原调用栈清空；
- 计时结束：计时器线程将回调函数塞进宏任务队列排队；
- 事件循环取出回调执行时，会重新建立一个全新的调用栈来执行回调，和原调用栈没有关系；
- 回调执行完毕：栈帧弹出，调用栈再次清空，等待下一个任务；

### 作用域链

作用域链是 JavaScript 中标识符（变量名、函数名、形参名等）解析的核心规则。它不是一份独立存储的变量列表，而是由当前词法环境及其连续的外部词法环境引用（OuterEnv）串联形成的链式结构，决定了变量查找的路径与可见范围

查找规则（单向从内向外）：

1. 先查询当前执行上下文的词法环境对应的环境记录；
2. 未找到则通过 `outer` 引用，查询外层词法环境的环境记录；
3. 持续向外层遍历，直到全局词法环境；
4. 全局环境仍未找到匹配绑定，抛出 `ReferenceError`。

```
const value = "global";

function createReader() {
  const value = "outer";

  return function read() {
    return value;
  };
}

const read = createReader();
read(); // "outer"
```

执行 `read()` 时的完整查找路径：

1. 先查 `read` 函数自身的环境记录：没有 `value` 绑定；
2. 通过 `outer` 引用找到 `createReader` 的词法环境：找到 `value = "outer"`，返回该值；
3. 查找终止，不会继续向外查找全局的 `value`；

**核心特性：词法作用域（静态作用域）**：作用域链的结构完全由代码书写的位置（词法结构）静态决定，和函数的调用位置、调用时机、调用栈结构都无关；ES6 引入 `let`/`const` 后，`{}` 代码块会创建独立的块级词法环境，同样会加入作用域链；

**暂时性死区（TDZ）的本质**：`let`/`const` 声明的变量，会先在环境记录中创建绑定，但不会初始化。在代码执行到赋值语句前访问该变量，就会触发报错 —— 这是作用域链查找的结果：能找到绑定，但绑定处于未初始化状态。

### VO 与 AO

VO（Variable Object，变量对象）和 AO（Activation Object，活动对象）是 ECMAScript 3 时代的核心教学模型，用于描述 JavaScript 执行上下文中的变量存储、变量提升等机制。随着 ES6 引入块级作用域、模块、类等新特性，规范已全面采用「词法环境 / 环境记录」体系；

- VO 每个执行上下文（全局上下文、函数上下文）都会关联一个变量对象，它是上下文的「变量容器」，所有在该上下文中定义的变量、函数声明、形参，都会作为属性挂载到这个对象上
- AO 本质就是函数执行上下文的 VO，二者是同一个对象在不同阶段的不同称呼：函数调用前，抽象的变量容器叫 VO，函数调用、进入执行上下文时：被激活并完成形参、`arguments` 等初始化叫 AO；

## 事件循环

ECMAScript（JS 语言标准）只定义语言本身（语法、原型、函数、对象），不包含 DOM、定时器、网络 IO；JS 引擎负责解析和执行 ECMAScript；并且宿主环境（浏览器 / Node.js）提供额外 API、事件循环、多线程等能力；

### 进程和线程


进程：是操作系统分配资源的最小单位，操作系统启动一个程序，就创建一个进程；每个进程拥有独立内存空间（虚拟内存）、文件描述符、CPU 时间片等资源；并且进程之间相互隔离；例如打开 Chrome，新建每一个标签页会创建独立的渲染进程，网页相关逻辑都运行在该渲染进程内，并且还会创建浏览器主进程、插件进程、网络进程（全局唯一）等；

线程：操作系统调度 CPU 的最小单位（一个 CPU 核心同一时刻只能跑一个线程），属于进程内部；一个进程里面可以开多个线程，共享这个进程的资源（堆、文件句柄），但每个线程有自己独立的调用栈和寄存器。以 Chrome 标签页的渲染进程为例，它内部包含多条线程：主线程包括 JS 引擎、渲染引擎与事件循环调度模块，还有合成线程、多个光栅线程等；

协程：是用户态的轻量级 “子程序”，跑在线程之上，不由操作系统内核调度，由代码自身控制切换，也叫微线程；协程依附于线程，同一时刻，一个线程上只能运行一个协程；协程是非抢占式：必须手动交出执行权（yield /await），不是操作系统强行切走。JS 中的 async/await 就是协程模型，协程切换发生在用户空间，开销远小于线程切换；单一线程上的多个协程只能实现并发，无法利用 CPU 多核并行执行；

并行：指多个任务同一时刻同时运行，需要多个 CPU 核心，依靠多个线程或进程才能实现

并发：并发指多个任务交替执行，宏观上看起来同时在跑，单个 CPU 核心通过快速切换任务实现；

### 浏览器引擎与JS宿主环境

WebKit 是苹果主导开发的全功能开源浏览器引擎，是一套完整的网页处理方案，同时集成了页面渲染能力与 JavaScript 执行能力。 它核心分为两大模块：

- WebCore：渲染引擎核心，负责 HTML 解析生成 DOM 树、CSS 解析生成 CSSOM、布局计算、页面绘制、原生事件处理等所有页面渲染相关工作；
- JavaScriptCore（简称 JSC）：内置的 JavaScript 引擎，负责解析、执行 ECMAScript 代码。

V8 + Blink 是 Google 主导的双组件浏览器引擎组合，两者是完全独立的模块，分别承担 JS 执行与页面渲染的职责，共同构成完整的网页处理能力。

1. Blink：纯渲染引擎，是 Google 从 WebKit 的 WebCore 分支分叉开发而来，专门负责 DOM 解析、CSS 样式计算、布局排版、图层绘制与合成、DOM 事件分发等所有渲染相关工作，本身不具备 JavaScript 执行能力。
2. V8：Google 开发的高性能 JavaScript 引擎，独立于渲染引擎存在，专门负责解析、编译、执行 JavaScript 代码，拥有即时编译（JIT）、分代垃圾回收等核心技术，是目前性能最强的 JS 引擎之一。

浏览器宿主环境：

- JavaScript 引擎：负责解析、编译并执行 JavaScript 脚本，严格实现 ECMAScript 语言规范，本身不具备 DOM、网络等宿主侧能力。典型代表为 Chrome 的 V8、Safari 的 JavaScriptCore。
- 渲染器（渲染引擎）：负责 DOM 树构建、CSS 样式解析、布局计算、图层绘制与合成，完成页面的视觉渲染；同时管理 DOM 事件的监听与原生分发。典型代表为 Chrome 的 Blink、Safari 的 WebCore。
- 网络模块：由浏览器内核提供的宿主能力，负责处理页面全量资源请求（HTTP 连接、资源加载、缓存管理等），独立于 JS 引擎运行。
- 事件循环：由浏览器宿主实现的调度逻辑，运行在渲染进程主线程上，负责调度宏任务、清空微任务、协调渲染时机，串联起 JS 执行与页面渲染的执行顺序。

Node.js 宿主环境：

> **Node.js 版本边界：** 以下组成以当前 Node.js 官方架构为例；V8、libuv、线程池和系统 I/O 的具体实现会随 Node.js 及其依赖版本、操作系统而变化。

- V8 引擎：承担 JavaScript 脚本的解析与执行工作，和浏览器端 V8 同源，完整实现 ECMAScript 规范。
- Node.js 核心 API：由 Node 封装并向 JS 层暴露系统级宿主能力，包括文件操作、网络通信、进程控制、二进制处理等。
- libuv：跨平台底层库，为 Node.js 提供事件循环的完整实现、线程池调度，以及文件 I/O 等异步操作的底层支撑；
- 而 TCP/UDP 等网络类异步操作，会直接对接操作系统的非阻塞 IO 能力，由操作系统内核直接参与完成

ECMAScript 规范中定义了 Agent（代理） 概念，一个标准的 Agent 包含：执行调用栈、JS 堆内存、微任务队列，是 JavaScript 代码的独立执行单元；

“JavaScript 是单线程”通常指同一个 Agent 内的普通 JavaScript 代码，同一时刻只会在一个调用栈上串行执行。 这并不代表浏览器或 Node.js 整个进程只有一个线程：宿主环境可以创建多个独立的 Agent，每个 Agent 运行在独立的操作系统线程上，比如浏览器的 Web Worker、Node.js 的 Worker Threads，都会创建全新的独立 JavaScript Agent，实现多线程并行执行 JS 代码；

### 同步任务与异步任务

同步任务：是直接进入 JS 引擎调用栈、按代码书写顺序串行执行的任务；当前任务执行完成前，调用栈被持续占用，后续代码必须等待，不能提前执行；例如，函数调用、同步DOM操作、`localStorage` 读写、`alert()`、同步 `XMLHttpRequest`；

异步任务：是发起后由宿主环境的其他模块 / 线程在后台处理，不占用调用栈等待结果的任务；任务完成后，对应的回调函数会被放入指定任务队列，等待调用栈清空后，再由事件循环调度进入调用栈执行；

教学资料常将异步回调分为 task（常称“宏任务”）和 microtask。更准确的浏览器调度顺序是：事件循环选择并执行一个可运行 task → 执行微任务检查点并持续处理到队列为空 → 浏览器按需更新渲染 → 进入后续循环。

#### 宏任务

浏览器规范通常使用 task，而不是“宏任务”这一正式术语。“宏任务”是为了与 microtask 对比而形成的常用教学名称。

task 的来源与队列由宿主规范定义。浏览器的一轮事件循环至多选择并执行一个可运行 task，随后执行微任务检查点；Node.js 则按 libuv 阶段和各阶段回调队列调度，不能直接套用浏览器的单 task 模型。

- 浏览器端常见 task：`setTimeout` / `setInterval` 回调、DOM 事件回调、网络处理回调、脚本处理等；渲染更新由 HTML 规范中的渲染机会与 rendering task source 等机制协调，不应简单等同为普通宏任务；
- Node.js 端常见：`setTimeout` / `setInterval`、`setImmediate`、文件 I/O 回调、网络请求回调；

浏览器的 task 并不是全部放在同一个全局队列里按“先进先出”执行。WHATWG HTML 规范允许一个事件循环关联多个任务队列，各任务源会映射到相应队列；同一任务源中的任务保持顺序，但浏览器从哪个包含可运行任务的队列取任务属于实现定义，不存在跨浏览器固定一致的任务源优先级表。

常见任务来源包括用户交互、网络活动、定时器、导航与历史遍历、DOM 操作和渲染更新等。`requestIdleCallback` 则由独立的空闲期调度机制安排，不宜作为固定“最低优先级宏任务”理解。

#### 微任务

ECMAScript 定义 Promise Job 等语言级作业及宿主入队钩子，具体队列与执行时机由宿主接入自己的调度模型：浏览器由 HTML 事件循环维护微任务队列；Node.js 除标准微任务队列外，还有独立的 `process.nextTick()` 队列。到达微任务检查点后，会持续处理队列，直到队列为空；

- 通用：`Promise.then/catch/finally`、`queueMicrotask()`
- 浏览器特有：`MutationObserver`
- Node.js 特有：`process.nextTick`（优先级高于普通微任务）

#### 微任务检查点

微任务不会随时抢占正在执行的 JavaScript 代码，也不是产生后立刻执行；浏览器宿主预设了固定的微任务检查点，只有到达检查点时，引擎才会批量处理微任务队列，持续执行直到队列为空；

浏览器通常会在以下时机执行微任务检查点：

- 页面初始同步脚本全部执行完成，函数调用栈完全清空；
- 任意一个宏任务回调（如定时器回调、点击事件回调、网络请求回调）执行完毕，调用栈弹出。

此时触发微任务检查点，一次性清空当前所有微任务；如果微任务执行过程中又产生新微任务，也会在本次检查点全部执行完，不会留到下一轮。

部分宿主 API 的回调执行结束后，W3C 规范明确要求必须执行一次微任务检查点，确保回调产生的微任务能在后续逻辑前落地。 常见场景包括：部分 DOM 原生事件回调执行完毕、IndexedDB 操作完成回调结束等

### 浏览器事件循环处理模型

ECMAScript 规范本身只定义了语言的执行逻辑，不包含任务调度能力。由于单个 JavaScript Agent 同一时刻只能在一个调用栈上串行执行代码（即常说的 “JS 单线程”），如果遇到定时器、网络请求等需要等待的操作，主线程就会直接阻塞。事件循环的作用就是：将异步操作的等待过程交给宿主后台模块处理，等待完成后将回调按规则排队，在合适的时机调度回主线程执行，让主线程在等待期间可以继续处理其他工作；

浏览器事件循环六阶段：

1. 选择并执行一个可运行任务：如果存在包含可运行任务的任务队列，事件循环以实现定义的方式选择其中一个队列，再取出该队列中最早的可运行任务并执行。这里的“任务”是宿主调度单元，其步骤可能在内部调用一个或多个回调。

 2. 任务结束后执行微任务检查点：当前整个宏任务单元执行完毕，JavaScript 调用栈完全清空后，触发微任务检查点：一次性清空全部微任务队列；执行过程中新产生的微任务也会在本次检查点内继续执行，直到微任务队列彻底为空，才会退出检查点。

3. 浏览器判断是否需要更新渲染：渲染不是每轮事件循环的必选项，浏览器会综合多个因素自主决定是否提供渲染机会：

	- 屏幕刷新率：普通屏幕为 60Hz，约 16.6ms 才会有一个渲染窗口，窗口期之前的多轮事件循环都只会处理任务，不会触发渲染；
	- 页面可见性：后台标签页会大幅降低渲染频率甚至暂停渲染，把 CPU 资源让给前台页面；
	- 视觉变更：如果 DOM、CSS 没有任何视觉变化，浏览器会跳过本次渲染；
	- 性能预算：低性能设备或页面压力大时，浏览器可能主动降频渲染。

 4. 处理渲染相关回调（requestAnimationFrame）：如果确定执行渲染，在正式渲染前会批量执行所有 `requestAnimationFrame`（rAF）注册的回调。这是渲染前最后一次修改 DOM 的时机，此时的修改会同步纳入本次渲染，不会造成额外的布局抖动。

5. 执行完整渲染流水线：依次执行完整的页面渲染步骤：样式计算（Style）→ 布局（Layout）→ 绘制（Paint）→ 图层合成（Composite），最终完成页面视觉更新。

 6. 进入下一轮事件循环：渲染完成后，回到第 1 步，继续等待并调度下一个任务单元。

### Node.js 事件循环

Node.js 的事件循环由 libuv 库实现，与浏览器是两套独立的调度模型；Node.js 没有 DOM 渲染环节，核心围绕异步 I/O、定时器、系统回调展开。主要阶段包括：

1. 待处理回调（pending callbacks）：执行上一轮循环中延迟下来的系统级回调（如 TCP 连接错误回调）；
2. idle、prepare：Node.js 内部使用，开发者通常不会直接接触；
3. 轮询阶段（poll）：核心 I/O 阶段，等待新的 I/O 事件并执行对应的 I/O 回调；队列为空时，根据定时器和 `setImmediate()` 等状态决定等待或进入下一阶段；
4. 检查阶段（check）：执行 `setImmediate()` 注册的回调；
5. 关闭回调（close callbacks）：执行资源关闭事件的回调（如 `socket.on('close')`）；
6. 定时器阶段（timers）：执行已达到时间阈值的 `setTimeout`、`setInterval` 回调；阈值表示最早可执行时间，不保证精确时间。

Node.js 存在两套独立的微任务队列，优先级有明确高低之分：

1. `process.nextTick()` 队列（最高优先级，Node 特有）
2. Promise / `queueMicrotask()` 微任务队列（标准微任务）

在普通回调检查点以及 CommonJS 顶层执行结束后，Node.js 通常会先清空 `process.nextTick()` 队列，再处理 Promise 和 `queueMicrotask()` 使用的微任务队列。递归安排 `process.nextTick()` 可能让 I/O 长期得不到执行。

```
Promise.resolve().then(() => {
  console.log("promise");
});

queueMicrotask(() => {
  console.log("microtask");
});

process.nextTick(() => {
  console.log("nextTick");
});

// 在 CommonJS 顶层通常先输出 "nextTick"
// Promise 与 queueMicrotask 按进入微任务队列的顺序执行
```

 浏览器与 Node.js 的事件循环主要差异：

| 方面               | 浏览器                    | Node.js                 |
| ---------------- | ---------------------- | ----------------------- |
| 主要阶段             | 用户事件、定时器、网络、消息等        | 定时器、I/O、check、close 等阶段 |
| 渲染步骤             | 有页面渲染机会                | 没有 DOM 渲染               |
| 特有高优先队列          | 无 `process.nextTick()` | 有 `process.nextTick()`  |
| `setImmediate()` | 通常没有                   | Node.js 提供              |
| Worker           | Web Worker             | `worker_threads`        |

## JavaScript 引擎

JavaScript 引擎是执行 JavaScript 代码的核心程序，核心职责是将人类可读的源代码转换为机器可执行的指令，同时完整管理运行时环境 —— 包括对象内存布局、调用栈、作用域链、垃圾回收、异常处理等。不同引擎（V8、JavaScriptCore、SpiderMonkey 等）的实现流水线存在差异，但核心架构遵循通用的分层执行模型

```
源代码
  ↓
词法分析 / 语法分析
  ↓
AST 与作用域信息
  ↓
字节码或基线机器码
  ↓
解释执行 / 基线执行
  ↓ 收集类型反馈
优化 JIT 编译
  ↓ 假设失效
反优化
```

### 词法分析

词法分析（Lexing / Tokenization）是整个流水线的第一步，由词法分析器逐字符扫描源代码，将连续的字符流切割为有语法意义的最小单元（Token）；

ECMAScript 规范定义的 Token 主要分为以下几类：

- 关键字与保留字：`const`、`let`、`function`、`return` 等语法关键字；
- 标识符：变量名、函数名、属性名等，支持 Unicode 字符与转义序列；
- 字面量：数字、字符串、布尔值、`null`、正则字面量、模板字符串等；
- 标点与运算符：`=`、`*`、`;`、`{}`、`+`、`.` 等分隔符与操作符；
- 注释：单行注释 `//`、多行注释 `/* */`，词法阶段会直接跳过；

```
const total = price * count;

// 可以抽象为：
Keyword(const)
Identifier(total)
Punctuator(=)
Identifier(price)
Punctuator(*)
Identifier(count)
Punctuator(;)
```

现代引擎不会先生成完整的 Token 数组再交给语法分析，而是语法分析器按需向词法分析器请求下一个 Token，边生成边解析，减少内存占用，提升解析速度；

### 语法分析与 AST

语法分析器（Parser）接收 Token 流，根据 ECMAScript 语法规则构建抽象语法树，同时完成语法合法性校验与元数据收集；

AST 是源代码语法结构的树形表示，只保留语义结构，丢弃空格、换行、注释等排版细节。例如 `const total = price * count;` 对应的简化 AST 结构：

```
VariableDeclaration (kind: const)
└── VariableDeclarator
    ├── Identifier: total
    └── BinaryExpression (operator: *)
        ├── Identifier: price
        └── Identifier: count
```

语法分析不只是生成 AST，还会同步完成多项关键检查与信息收集：

- 作用域分析：构建全局作用域、函数作用域、块级作用域的层级关系，确定每个标识符的绑定位置，为后续变量查找、闭包处理提供基础。
- 语法合法性校验：检查 `let/const` 重复声明、`await` 出现在 async 函数外、`break/continue` 脱离循环 /switch 等语法错误。
- 严格模式识别：识别 `"use strict"` 指令，启用严格模式下的语法限制。
- 重复声明检查：同一作用域内同名函数、变量的声明冲突检测。

延迟解析：引擎不会一次性完整解析所有函数，而是分为两个阶段：

- 预解析：快速扫描函数外层，只验证语法正确性、识别参数列表与函数边界，不生成完整 AST，速度极快。
- 全量解析：只有当函数第一次被调用时，才会对函数体做完整语法分析，生成 AST 并编译为字节码。

社区有通用的 AST 规范（ESTree），Babel、ESLint、代码压缩工具都基于此标准；但引擎内部使用的 AST 通常更精简，会额外附带字节码生成所需的元数据，与社区标准不完全一致；

### 字节码

字节码是介于源码与机器码之间的中间表示，是解释执行的基础。现代主流 JS 引擎都会先将 AST 编译为字节码，再交由解释器执行。

```
function add(a, b) {
  return a + b;
}

// 概念上的字节码可能表示为：
LoadArgument 0
Add Argument 1
Return
```

字节码面向虚拟机设计（栈式或寄存器式），具有以下特点：

- 生成速度快：相比高度优化的机器码，字节码编译逻辑简单，生成速度快，能快速进入执行阶段。
- 体积紧凑：通常比源码小很多，内存占用更低。
- 架构无关：不绑定具体 CPU 架构（x86、ARM 等），同一套字节码可以在不同硬件的解释器上运行。
- 便于收集反馈：解释执行过程中可以方便地收集类型、调用等运行时反馈，为后续 JIT 优化提供输入。

并非所有代码 / 所有阶段都必须经过字节码：部分引擎的 JIT 编译器可以直接从 AST 生成机器码，跳过字节码阶段；极简单的代码也可能直接被优化编译；

### 解释器

解释器读取字节码，逐条解析执行，同时处理 JavaScript 的动态语义，是代码首次执行的核心载体

解释器的核心职责

- 执行基础运算：算术、比较、逻辑运算，处理 JS 弱类型的隐式转换规则。
- 变量与属性操作：基于作用域链查找变量，基于原型链完成对象属性的读写。
- 流程控制：处理分支、循环、函数调用与返回、异常抛出与捕获。
- 运行时调度：调用引擎内置的运行时辅助函数（如数组方法、对象方法）。
- 类型反馈收集：在每个操作位置记录运行时的类型、对象结构等信息，存入反馈向量，为 JIT 优化提供数据支撑。

解释器启动快，适合首次执行和低频代码，但逐条解释通常不如优化后的机器码高效。

### JIT 编译器

JIT（即时编译）是现代 JS 引擎性能飞跃的核心：在运行过程中，将高频执行的 “热点代码” 编译为机器码，并基于运行时反馈做深度优化，最终性能接近原生 C/C++ 代码。

JS 引擎普遍采用分层编译架构，在启动速度、内存占用和峰值性能之间取得平衡。优化层级越高，生成的机器码越快，但编译耗时越长、内存开销越大。

通用的四层执行模型（不同引擎命名与层级数量有差异）：

| 层级     | 执行方式    | 特点                          | 适用场景          |
| ------ | ------- | --------------------------- | ------------- |
| Tier 0 | 解释器     | 启动最快、执行最慢，收集基础类型反馈          | 冷代码、首次执行、低频代码 |
| Tier 1 | 基线编译器   | 快速生成轻量优化的机器码，编译速度快，继续收集详细反馈 | 中度热点代码        |
| Tier 2 | 中层优化编译器 | 中度优化，编译速度与性能平衡              | 中高频热点代码       |
| Tier 3 | 顶层优化编译器 | 深度激进优化，执行速度接近原生，编译耗时久       | 高频热点代码        |

优化编译器基于类型反馈做出激进假设，实现多种高性能优化：

- 类型特化：针对收集到的稳定类型生成专用机器码，省略运行时的类型检查与分支。例如一直接收数字的加法函数，直接生成 CPU 原生加法指令，仅保留一个类型哨兵检查。
- 函数内联：将体积小、调用频繁的函数代码直接嵌入调用处，消除函数调用的栈帧开销、参数传递开销，是收益最高的优化之一。
- 常量折叠与死代码消除：编译期计算常量表达式的结果，删除永远不会执行的代码，减少运行时计算量。
- 循环优化：循环展开、循环不变量外提、强度削弱（如将乘法替换为加法），降低循环的执行开销。
- 逃逸分析与标量替换：分析对象是否只在函数内部使用（不逃逸到外部），如果不逃逸则直接在栈上分配对象，甚至将对象属性拆分为独立变量（标量替换），完全消除堆分配与 GC 压力。
- 数组边界检查消除：如果能证明数组下标始终在合法范围内，移除数组访问的边界检查代码
### 类型反馈

JavaScript 是动态类型语言，变量与对象没有固定类型，但运行时往往表现出稳定的结构特征。引擎通过类型反馈记录这些特征，并通过隐藏类技术将动态对象转化为类似静态语言的固定内存布局

#### 隐藏类

隐藏类（V8 内部称为 Map，注意与 JS 内置 `Map` 区分）是引擎为对象抽象的 “结构描述符”，记录了对象拥有的所有属性名称、属性类型、以及每个属性在对象内存中的偏移量。

核心原理

- 所有结构完全相同（属性名称、添加顺序完全一致）的对象，共享同一个隐藏类。
- 访问对象属性时，无需做哈希表查找，直接根据隐藏类中记录的偏移量，到对象内存的对应位置取值，速度与 Java 等静态语言的对象访问相当。

 隐藏类的变迁：当给对象添加新属性时，引擎会创建过渡隐藏类，对象的隐藏类指针指向新的隐藏类，形成隐藏类链。

```
function Point() {
  this.x = 1; // 初始隐藏类 C0 → 添加 x 属性 → 过渡到 C1
  this.y = 2; // C1 → 添加 y 属性 → 过渡到 C2
}
const p1 = new Point();
const p2 = new Point();
// p1 和 p2 按相同顺序添加属性，最终共享隐藏类 C2
```

如果属性添加顺序不同，会生成完全不同的隐藏类链，无法共享结构：

```
const a = {}; a.x = 1; a.y = 2; // 隐藏类链：C0→C1→C2
const b = {}; b.y = 2; b.x = 1; // 隐藏类链：C0→C3→C4
// a 和 b 最终属性相同，但隐藏类不同
```

属性存储模式：

- 快属性模式：有隐藏类的对象，属性通过偏移量访问，速度快。属性分为内联属性（存在对象本身内存中，访问最快）和外排属性（存在额外属性数组中，多一次寻址）。
- 慢属性模式（字典模式）：当对象频繁增删属性、隐藏类变迁过于频繁时，引擎会将对象退化为哈希字典模式，属性通过哈希表查找，访问速度变慢，但增删属性无需修改隐藏类。

#### 类型反馈的收集

代码在解释器 / 基线编译器运行时，引擎会在每一处操作（读属性、调函数、做运算等）记下每次运行的真实类型和规律，存到反馈向量里（即运行的日志），给后面 JIT 优化当依据；

主要收集 4 类信息：

- 属性访问：对象的结构类型、属性在内存中的位置；
- 函数调用：调用的是不是同一个函数、参数都是什么类型；
- 算术运算：参与运算的值是数字、字符串还是其他类型；
- 分支判断：if/else 哪条路走得更多；

为了保证快路径不会输出错误结果，优化后的机器码中会在关键位置插入哨兵检查：在执行快速逻辑前，先验证当前输入是否符合优化假设（比如参数是不是数字、对象隐藏类是否匹配）。

- 如果假设成立：继续执行快速路径，获得高性能；
- 如果假设不成立：立即触发反优化（Deoptimization），丢弃当前的优化机器码，回退到解释器执行通用的完整逻辑，保证输出结果完全符合 ECMAScript 规范。
### 内联缓存

Inline Cache（IC）是基于类型反馈的运行时优化技术，在每个操作位置（调用点）缓存之前遇到的对象结构与处理方式，避免每次执行都做完整的属性查找 / 类型判断。

每个调用点的 IC 会根据遇到的结构数量，处于不同状态：

1. 未初始化（Uninitialized）：从未执行过，没有任何缓存信息。
2. 单态（Monomorphic）：只遇到过一种隐藏类 / 类型，缓存了对应处理逻辑。执行时只需一次类型检查，直接走缓存路径，速度最快。
3. 多态（Polymorphic）：遇到过少量（通常 2~4 种）不同的隐藏类 / 类型，缓存了多组逻辑。执行时需要依次检查匹配的结构，性能低于单态，但仍远快于全量查找。
4. 超多态（Megamorphic）：遇到的结构数量超过阈值，不再缓存单个情况，直接走通用运行时查找路径，性能最差。

以属性访问 `function getName(user) { return user.name; }` 为例：

- 第一次调用传入 `{name: "Alice"}`，隐藏类为 C1，IC 从未初始化变为单态，缓存 C1 与 `name` 的偏移量。
- 后续调用传入相同结构的对象，直接通过偏移量快速取值。
- 当传入另一种结构的对象 `{name: "Bob", age: 20}`（隐藏类 C2），IC 变为多态，同时缓存 C1 和 C2 的偏移量。
- 如果继续传入大量不同结构的对象，超过阈值后 IC 退化为超多态，不再使用缓存。

除了属性访问 IC，还有函数调用 IC、运算 IC 等，原理类似，都是通过缓存历史结果减少重复计算；

### 优化与反优化

JIT 优化的所有激进假设都依赖历史运行数据，一旦后续执行打破了这些假设，引擎必须触发反优化：丢弃优化后的机器码，回退到解释器或基线代码执行，保证语义正确性

常见的反优化触发场景

- 类型突变：热点函数之前一直接收数字参数，突然传入字符串、对象等其他类型。
- 对象结构变化：给已优化的对象新增、删除属性，导致隐藏类与缓存不匹配。
- 原型修改：动态修改构造函数的 `prototype` 或对象的 `__proto__`，会导致所有相关的属性访问假设失效。
- 数组模式切换：数组从连续数字元素变为包含非数字元素、稀疏数组等不同元素模式。
- 函数替换：被内联的函数被重新赋值，内联代码失效。
- 异常抛出：优化代码中很少考虑异常路径，抛出异常时通常会触发反优化。

反优化的执行过程：优化后的机器码中会插入很多哨兵检查，一旦检查失败（假设不成立），立即触发反优化：

1. 保存当前执行上下文：将优化代码的寄存器、栈帧状态转换为解释器可识别的格式。
2. 丢弃优化后的机器码，回退到解释器或基线代码继续执行。
3. 重新收集类型反馈，如果后续运行再次稳定，可能重新触发优化编译。

## 内存管理与垃圾回收

JavaScript 是一门自动管理内存的语言，引擎通过垃圾回收（Garbage Collection, GC）机制自动释放不再使用的内存；

### 栈内存与堆内存

JavaScript 运行时的内存被抽象为栈（Stack）和堆（Heap）两大区域，分别承担不同的存储职责：

- 栈内存：保存函数调用栈的执行帧，以及帧内的局部变量、函数参数、返回地址等基础数据。栈内存是连续的空间，函数执行结束后，对应的栈帧会自动弹出，内存随之释放，分配与回收效率极高。
- 堆内存：保存对象、数组、闭包环境等动态、大小不固定的数据。堆内存是离散分配的，不会自动释放，需要垃圾回收器来管理生命周期。

```
function createUser(name) {
  // user 是局部变量，存在栈中；它保存的是堆中对象的引用地址
  const user = { name };
  return user;
}
const currentUser = createUser("Alice");
// 函数执行完，栈内的 user 变量销毁；堆中的对象被 currentUser 引用，继续存活
```

现代 JS 引擎会做大量底层优化，实际内存布局远比模型复杂：

1. 寄存器分配：高频使用的变量会直接分配到 CPU 寄存器，比栈内存访问更快。
2. 逃逸分析：引擎分析对象的作用域，如果对象不会 “逃出” 当前函数（没有被返回、没有被外部闭包引用），就不会在堆上创建它。
3. 标量替换：基于逃逸分析，把未逃逸的对象拆解成多个独立的原始字段，直接分配在栈或寄存器上，完全消除对象的内存开销。
4. 指针压缩：64 位系统下，引擎通过对齐规则将 8 字节的指针压缩为 4 字节，大幅减少对象内存占用，提升 CPU 缓存命中率。
5. 栈上分配：满足逃逸分析条件的小对象，直接分配在栈内存中，函数执行完自动释放，无需 GC 介入。

### 可达性分析

现代 JavaScript 引擎的垃圾回收以可达性为核心判断标准，而非简单的引用计数

垃圾回收器从一组被称为 GC Roots（根对象） 的集合出发，沿着引用关系遍历，所有能被遍历到的对象都是 “可达” 的，会被保留；无法到达的对象会被回收。

常见的 GC Roots 包括：

- 当前执行栈中的引用：局部变量、函数参数、临时变量等。
- 全局对象：浏览器的 `window`、Node.js 的 `globalThis`，以及所有全局变量。
- 活跃闭包引用的外层作用域环境。
- 宿主持有的任务：事件监听器回调、定时器回调、网络请求回调、Promise 回调等。
- 引擎内部常驻对象：内置构造函数原型、核心 API 对象等。

```
let user = {
  profile: {
    name: "Alice",
  },
};

 //虽然 `user` 被清空，但 `profile` 仍然引用内部对象，所以该对象仍然可达。
let profile = user.profile;
user = null;
```

循环引用是引用计数算法的致命缺陷，但在基于可达性的标记式 GC 中完全不存在：从 GC Roots 出发无法访问到互相引用的对象，因此它们会被整体回收；

```
let first = {};
let second = {};
first.other = second;
second.other = first; // 形成循环引用

first = null;
second = null;
```

### 标记清除法

标记 - 清除是最基础的 GC 算法，也是现代引擎的核心框架，分为两个阶段：

1. 标记阶段：从 GC Roots 出发，递归遍历所有可达对象，给它们打上标记。
2. 清除阶段：遍历整个堆内存，回收所有没有被标记的对象，将释放的内存加入空闲链表。

清除后会产生大量离散的内存碎片，大对象可能找不到连续的空闲空间分配，为了解决碎片与效率问题，实际引擎会结合多种策略：

1. 标记 - 压缩：标记完成后，将所有存活对象移动到堆内存的一端，再清理掉边界外的所有内存。优点是消除内存碎片，缺点是移动对象需要更新所有引用，开销较高。
2. 复制算法：将内存分成大小相等的两块，每次只使用其中一块。回收时把存活对象完整复制到另一块，再清空当前块。优点是无碎片、分配速度快；缺点是内存利用率只有 50%。

引用计数通过记录对象被引用的次数判断是否回收，引用数为 0 就释放。它实现简单、回收及时，但存在无法解决的缺陷：

- 无法处理循环引用，是最致命的问题。
- 每次赋值都要增减引用计数，额外开销大。
- 多级引用释放时会引发连锁递归，可能导致卡顿。

### 分代垃圾回收机制

分代回收的全部设计都建立在弱分代假说之上，这是从大量真实程序运行中总结出的经验规律：

1. 绝大多数对象生命周期极短：新创建的对象大部分很快就会变成不可达状态（“死亡”）；
2. 存活越久的对象，越可能继续存活：熬过多次回收的对象，通常会在内存中存在很长时间。

基于这个规律，没有必要每次回收都扫描整个堆内存。将堆按 “对象年龄” 划分为不同代，对 “死得快” 的区域频繁回收、对 “活得久” 的区域低频回收，可以大幅降低 GC 的整体开销，显著提升回收效率

主流引擎通常将堆逻辑上划分为两大核心代际：

- 新生代：存放新创建对象，回收频繁，区域较小；
- 老生代：存放经过多次回收仍存活的对象，回收频率较低。

新生代常使用复制或区域交换策略。对象多次存活后会晋升到老生代。

各代际的回收算法：

- 新生代：复制算法与 Minor GC，新生代采用复制算法，执行 Minor GC 时，会把 Eden 区和一块 Survivor 区中的存活对象，整体复制到另一块空的 Survivor 区并连续排列，随后直接清空原区域；
- 老生代：标记 - 清除 / 标记 - 整理与 Major GC，老生代执行 Major GC 以标记类算法为主：标记 - 清除算法先标记存活对象，再直接回收死亡对象，实现简单但会产生内存碎片；标记 - 整理算法在标记后，会将存活对象统一移动到内存一端再清理剩余空间，能彻底消除碎片，但执行开销更高。实际引擎通常组合使用两种算法，平衡效率与内存利用率；

### WeakMap 与 WeakSet

弱引用不会计入 JS 垃圾回收（GC）的强引用计数。 如果一个对象只有 WeakMap / WeakSet 持有它的引用，没有其他任何变量、对象强引用指向它，GC 就可以回收这个对象； 普通 `Map` / `Set` 是强引用，只要 Map 还在，里面的对象就不会被回收，容易造成内存泄漏。

WeakMap 的键和 WeakSet 的成员采用弱关联语义，不会单独阻止目标被回收。WeakMap 条目并不是“弱 key + 普通强 value”的简单组合：即使 value 反向引用了 key，只要 key 无法从 WeakMap 条目之外的强引用路径到达，这个反向引用也不会单独让 key 保持存活；

WeakMap 对键保持弱关联：如果某个键不再被其他强引用访问，仅仅出现在 WeakMap 中不会阻止它被回收。不支持：

- `size` 属性
- `keys()` / `values()` / `entries()`
- `forEach()`
- 不能迭代（`for...of`）
- 没有 `clear()` 方法

GC 什么时候回收对象是不确定的。如果 WeakMap / WeakSet 可以遍历，代码就能检测作为弱引用键的对象是否还存在，从而知道 GC 在这一刻执行了回收。为了不让代码观测到 GC 的行为，ES 规范直接禁止遍历；

```
const wm = new WeakMap();
// 仅支持：对象 / 未注册的 Symbol 作为 key
wm.set(keyObj, value);
wm.get(keyObj);
wm.has(keyObj);
wm.delete(keyObj);
```

WeakSet 对集合内成员使用和 WeakMap 完全一致的弱关联语义，同样没有 size、不能迭代、无 clear ()，理由和 WeakMap 完全一致；

```
const ws = new WeakSet();
ws.add(obj);
ws.has(obj);
ws.delete(obj);
```

WeakMap 键和 WeakSet 成员通常使用对象；现代规范也允许不可注册的 Symbol。通过 `Symbol.for()` 获得的全局注册 Symbol 不能作为弱集合键。

### WeakRef 与 FinalizationRegistry

WeakRef 的核心作用是创建目标对象的弱引用：

- 弱引用不会给对象增加 “存活计数”，不阻止 GC 回收目标对象；
- 当目标对象失去所有强引用后，GC 可以在任意时机回收它；
- 回收后再通过 `deref()` 访问，会返回 `undefined`。

在同一个独立执行单元（Job）中，比如一段同步脚本、一个事件回调、一个 Promise 回调或定时器回调中，一旦通过 `deref()` 获取到了目标对象，那么在这个Job 结束前，该对象都会保持存活状态，不会在同一个执行流程中间突然被回收，因此在同一段同步代码中多次调用 `deref()` 得到的结果是一致的，不会出现前后不一致的情况；

```
let user = { name: "Alice" };
// 创建指向 user 的弱引用
const reference = new WeakRef(user);

// 当前对象未被回收，可获取原对象
reference.deref(); // { name: 'Alice' }

// 断开强引用，对象失去所有强引用后可被垃圾回收
user = null;

// 此时调用 deref() 结果不确定，不会立刻变为 undefined
reference.deref(); // 未来某次调用可能得到 undefined
```

FinalizationRegistry 允许开发者注册目标对象，并请求在目标对象被回收后的某个时间执行清理回调；但规范不保证目标何时被回收，也不保证清理回调一定会执行，因此它只能承担非关键的辅助清理，不能作为保证资源释放或业务正确性的机制；

常见主动清理机制：

- removeEventListener()：移除 DOM 元素或事件目标上绑定的监听器，切断回调与目标对象的引用关联；
- clearInterval() / clearTimeout()：销毁定时器，停止周期性 / 延迟回调的执行，释放定时器任务与闭包引用；
- AbortController.abort()：Web 标准的中止控制器，可批量取消 `fetch` 请求、DOM 事件监听、流操作等异步任务；
- 流的 cancel()：终止流的读写流程，释放底层的网络连接、文件句柄、缓冲区等系统资源；

```
// 1创建注册中心，回调参数是注册时传入的 heldValue（持留值/清理令牌）
const registry = new FinalizationRegistry((heldValue) => {
  // 目标对象被GC后，该回调异步批量触发
  console.log('对象已回收，执行清理：', heldValue);
  // 在这里执行辅助清理逻辑
});

// 注册目标对象：第二个参数是 heldValue，第三个参数是可选的 unregister token
const target = { name: 'demo' };
registry.register(target, 'cleanup-token-001', target);

// 必须传入注册时使用的 unregister token；这里使用 target 自身作为 token
registry.unregister(target);
```

### 常见内存泄漏

对象已经不再被业务需要，但仍然被根对象间接可达， GC 判定它仍在使用，无法释放内存；

意外全局引用：全局变量永远被根对象直接可达，只要不手动断开，就永远不会被回收；

```
// 未开启 'use strict' 时
function init() {
  // 缺少 let/const，自动变成 window.largeData
  largeData = new Array(1_000_000).fill(0);
}

function Store() {
  // 直接调用 Store() 时，this 指向 window
  this.cache = new Array(100_000).fill('data');
}
Store();
```

未清理的事件监听器：事件回调本质是闭包，会持有外部作用域的所有引用；只要监听器不移除，回调和它引用的对象就永远无法回收；

```
// 反面示例：匿名回调无法移除
button.addEventListener('click', () => {
  console.log(largeData.length);
});
```

未停止的定时器：`setInterval`、递归 `setTimeout` 轮询如果不主动清除，会持续运行；回调闭包持有的外部上下文会永久存活

闭包保留大型对象：闭包本身不会造成内存泄漏，泄漏的根源是：闭包被长期持有（挂到全局、事件、定时器），间接持有了本不需要的大对象

未完成或没有取消的请求、订阅和流：网络请求、WebSocket、可读流、消息订阅等异步任务，不仅占用系统资源，其回调还会持有上下文对象，造成连锁泄漏
