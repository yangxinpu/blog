## 浏览器运行时

### 浏览器进程与线程

现代浏览器采用多进程架构，核心目的是安全隔离与稳定性—— 单个页面崩溃不会影响整个浏览器，不同站点之间通过进程沙箱隔离数据：

- 浏览器进程：浏览器的 “大脑”，管理窗口创建 / 销毁、地址栏导航、权限控制、文件访问、进程调度与协调；
- 渲染进程：执行 JS、解析 HTML/CSS、完成布局、绘制与合成；
- GPU 进程：负责 GPU 资源调度、3D 渲染、图层合成与纹理上传；全局唯一，为所有渲染进程提供硬件加速能力；
- 网络进程或网络服务：统一处理所有 HTTP/HTTPS 请求、缓存管理、Cookie 处理；
- 扩展、插件或工具进程：每个浏览器扩展、第三方插件运行在独立进程中；

“一个标签页对应一个进程” 是常见误区，实际分配由「站点隔离策略」决定：

- 跨站的页面（不同一级域名）一定运行在不同渲染进程中，防止恶意页面读取跨站数据；
- 同站的多个标签页、同站的 iframe，可能共享同一个渲染进程；
- 设备内存不足时，浏览器会合并部分渲染进程以节省资源

### 渲染进程模型

每个渲染进程内部是多线程协作模式，核心线程分工明确；

**渲染主线程**：渲染进程最核心的线程，单线程执行（JS 执行与 DOM 操作共用同一线程），承担所有关键工作：

- 解析 HTML 生成 DOM、解析 CSS 生成 CSSOM；
- 执行页面 JavaScript 代码（包括内联脚本、外部脚本、事件回调、定时器、微任务）；
- 样式计算、布局计算、生成绘制记录；
- 处理用户输入事件（点击、滚动、键盘等）；
- 协调渲染帧的完整流程。

单线程原因：DOM 是共享状态，多线程并发修改会引发复杂的线程安全问题；从设计上避免了并发冲突，也简化了 Web 编程模型。

**合成线程**：独立于主线程运行，负责图层合成与滚动处理：

- 接收主线程提交的图层与绘制记录；
- 将图层分块（Tile）交给光栅化线程；
- 处理页面滚动、图层变换、透明度调整；
- 把最终合成的帧提交给 GPU 进程显示。

关键特性：合成线程可以不等待主线程直接处理滚动和 transform/opacity 动画，这是 “硬件加速动画流畅” 的核心原因。但如果动画触发了布局或重绘，仍会回退到主线程处理；

**光栅化线程池**：负责把绘制指令转换为实际像素数据（位图 / 纹理），支持多线程并行处理；支持 GPU 加速光栅化，大幅提升绘制效率；

**其他辅助线程**：

- 网络 IO 线程：负责和网络进程通信，接收资源数据；
- 定时器线程：管理 setTimeout/setInterval 的计时；
- Web Worker 线程：独立的 JS 执行线程。

### 完整渲染流水线

从 HTML、CSS 等资源到屏幕像素，可以把浏览器渲染流水线简化为：资源加载与解析 → 样式计算 → 布局 → 预绘制与绘制 → 提交与分层 → 光栅化 → 合成与显示

各阶段并非每一帧都会完整执行。浏览器会根据页面变化跳过不需要的阶段，例如某些合成层上的`transform`动画可以跳过布局和绘制。下面主要以 Chromium/Blink 的实现为例，不同浏览器的内部名称和细节可能不同。

#### DOM 与 CSSOM 构建

**DOM 树构建**

HTML 解析是流式增量解析，边接收网络数据边构建，分为两步：

1. 字节解码与分词：将 HTML 字符流解析为开始标签、结束标签、文本等 Token；
2. 树构建：根据 Token 层级关系，创建 DOM 节点并构建 DOM 树。

HTML 解析器发现图片、脚本、样式表等外部资源后会发起请求。解析器被同步脚本阻塞时，预加载扫描器仍可扫描后续 HTML，提前请求可能需要的资源，但它不会替代主解析器构建 DOM。

**脚本对解析的阻塞**

普通同步脚本`<script src="xxx.js"></script>`会阻塞 HTML 解析：浏览器需要等待脚本下载并执行完成后再继续解析，因为脚本可能通过`document.write()`等方式影响后续文档结构。

- `defer`脚本并行下载，在 HTML 解析完成后、`DOMContentLoaded`之前按文档顺序执行；
- `async`脚本并行下载，下载完成后尽快执行，不保证执行顺序，执行时仍会占用主线程；
- `type="module"`脚本默认具有类似`defer`的行为。

**CSSOM 构建**

浏览器会把 CSS 解析为 CSSOM（CSS 对象模型），供后续样式计算使用：

- 浏览器遇到外部样式表时，会发起下载请求，但通常仍会继续解析 HTML、构建 DOM；
- 为了避免先显示无样式页面，`<head>`中适用于当前页面的样式表通常会阻塞首次渲染，直到样式表下载并解析完成；
- 如果 HTML 解析器遇到普通同步脚本，该脚本通常要先等待前面已发现的阻塞样式表加载完成。同步脚本又会阻塞 HTML 解析，所以 CSS 可能通过脚本间接阻塞 DOM 构建；
- 不影响当前页面显示的样式表通常不会阻塞首次渲染，例如屏幕环境中的`media="print"`样式表；`preload`样式表只负责提前下载，在正式应用前也不会阻塞渲染。

DOM 和 CSSOM 可以增量构建，资源加载、HTML 解析和 CSS 解析也可能交错进行，并不是严格串行完成后才进入下一步。

#### 样式计算与布局树构建

**样式计算（Style）**

浏览器根据 DOM 和 CSSOM 计算每个元素的样式：

- 匹配 CSS 选择器，处理层叠、继承和默认样式；
- 生成元素的计算样式；
- `em`、`rem`等值通常可以在此阶段解析，但百分比、`auto`以及依赖包含块尺寸的值，可能要到布局阶段才能确定最终使用值。

**布局树（Layout Tree）**

浏览器根据 DOM 结构和计算样式建立用于布局的盒/片段结构。传统资料常把它称为“渲染树”，但现代浏览器内部通常使用更细分的布局对象和片段树：

- `display: none`的元素及其后代不生成布局盒；
- `<head>`、`<script>`等非视觉内容通常不生成布局盒；
- `visibility: hidden`的元素仍生成布局盒并占据空间，只是不绘制可见内容；
- `display: contents`元素自身通常不生成盒，但其子元素仍可参与布局；
- `::before`、`::after`等伪元素不是 DOM 节点，但满足生成条件时可以生成布局盒；
- DOM 节点与布局对象不是一一对应的，例如文本换行后可能产生多个布局片段。

#### 布局

布局（Layout，页面更新时也常称重排 Reflow）负责计算几何信息：

- 输入：布局树、计算样式和视口等约束；
- 输出：布局对象/片段的尺寸、位置和相互关系；
- 浏览器分别执行普通流、Flex、Grid、浮动、定位等布局算法；
- 浏览器会尽量只重新计算受影响的部分，但修改根节点、视口尺寸或影响范围较大的属性时，可能引发大范围布局。

#### 预绘制与绘制

**预绘制（Pre-paint）**

在 Chromium 中，预绘制阶段会遍历布局结果，更新变换、裁剪、滚动、透明度等属性树，确定绘制失效区域，并为后续绘制准备数据。

**绘制（Paint）**

- 浏览器按照堆叠上下文和绘制顺序，生成背景、边框、文字、阴影、图片等绘制指令；
- 绘制指令描述“画什么、按什么顺序画”，此时通常还没有生成最终屏幕像素；
- 修改`color`、`background`、`box-shadow`等不影响几何结构的属性时，通常会触发样式计算和绘制，但可以跳过布局。

#### 提交、分层、光栅化与合成

**提交与分层**

主线程把绘制记录和属性树提交给合成线程。合成线程根据内容、变换、裁剪、滚动和动画等信息进行分层，使部分内容能够独立光栅化或独立合成。

以下情况可能促使浏览器创建独立合成层，但都不是跨浏览器、无条件的保证：

- 3D 变换或可在合成线程运行的`transform`、`opacity`动画；
- `will-change: transform`等合成提示；
- `video`、Canvas、WebGL、某些 CSS 滤镜；
- 固定定位元素、滚动容器等。

合成层需要额外的显存/内存和管理成本，层数过多可能降低性能。`will-change`只应在确有需要时使用，并在效果结束后移除。

**瓦片分块与光栅化**

- 较大的图层会被划分为多个瓦片（Tile），具体尺寸由浏览器、设备和运行状态决定；
- 浏览器通常优先处理视口内或即将进入视口的瓦片；
- 光栅线程把绘制指令转换为位图/纹理，光栅化既可能使用 CPU，也可能使用 GPU 加速；
- 光栅化结果会被上传或保存在 GPU 可使用的资源中。

**合成与显示**

合成线程根据图层的层级、裁剪、透明度、变换和滚动位置生成合成帧；随后由 GPU/显示合成系统组合纹理并提交给屏幕显示。

- 修改`transform`和`opacity`时，如果相关内容已经位于可独立合成的层上，并且没有引起其他绘制依赖，动画可能只触发合成，跳过布局和绘制；
- 这不是绝对规则，是否提升为合成层以及能否跳过前序阶段由浏览器根据页面状态决定。

#### 页面更新时的三种典型路径

1. 修改几何属性，如`width`、`height`、`margin`：样式计算 → 布局 → 预绘制 → 绘制 → 光栅化 → 合成；
2. 修改绘制属性，如`color`、`background`、`box-shadow`：样式计算 → 预绘制/绘制 → 光栅化 → 合成，通常跳过布局；
3. 修改可独立合成的属性，如合成层上的`transform`、`opacity`：可能只更新属性树并合成，跳过布局、绘制和重新光栅化。

### requestAnimationFrame

`requestAnimationFrame`（简称 rAF）是浏览器专门为视觉更新与动画场景设计的帧同步调度 API，它会将回调函数与浏览器的渲染节奏、显示器刷新节奏对齐，在下次屏幕刷新前统一执行，是 Web 端实现流畅动画的标准方案；

浏览器每一帧的完整执行顺序大致如下，rAF 回调处于渲染流程的最前端：

1. 处理用户输入事件（点击、滚动、键盘输入等）
2. 执行宏任务队列中的待办任务
3. 清空当前所有微任务队列
4. 执行所有 requestAnimationFrame 回调
5. 执行样式计算（Style）、布局（Layout）、绘制（Paint）
6. 合成线程进行图层合成（Composite），最终提交画面到显示器

也就是说，rAF 回调会在每一次 DOM 渲染更新之前执行，此时修改样式、操作 DOM 会被当前帧一并渲染，不会出现中间闪烁态

执行频率由显示器刷新率决定：60Hz 屏幕约每 16.7ms 执行一帧，144Hz 屏幕约每 6.9ms 执行一帧，不是固定的时间间隔；

每次调用 `requestAnimationFrame(callback)` 只会注册一次回调，回调执行后自动失效。 如果要实现连续动画，需要在回调内部递归调用 `requestAnimationFrame`，再次注册下一帧的回调：

```
function animate(timestamp) {
  position += 2; // 每帧移动 2px
  element.style.transform = `translateX(${position}px)`;
  requestAnimationFrame(animate);
}
```
